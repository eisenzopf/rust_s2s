# ADR 0002 — Streaming inference hot path: cuBLASLt + cuda-oxide kernels on one stream

| | |
|---|---|
| Status | Accepted (M4) |
| Date | 2026-11-09 |
| Refines | ADR 0001 (which model each kernel class uses) |

## Context

Real-time full-duplex inference steps the model once per 80 ms frame, at batch 1. For Moshi 7B a frame is:

- one temporal-transformer step (32 layers);
- eight depformer slices (6 layers each, own weights), each ending in a sample that feeds the next slice.

That is about 1,000 kernel launches and 9 host round trips per frame. At batch 1, every GEMM is a matrix-vector product bound by memory bandwidth. Moshi's 15.4 GB of bf16 weights take about 18 ms to read on an L40S (864 GB/s). The rest of the budget goes to the Mimi codec, the server and slack, so **launch overhead and host synchronization matter more than kernel arithmetic**.

ADR 0001 assigns dense math (norms, RoPE, attention, …) to cuTile and sparse work to cuda-oxide. In bring-up, cuTile proved itself (all parity tests pass on an L40S), but its host API does not suit this hot path:

- **JIT shape specialization.** Kernels are JIT-specialized on `const` shape generics. Shapes that change every step, such as the attention length `n`, would recompile, or would need masking that cuTile's tile ops make awkward.
- **Ownership and sync.** Launches move tensors in and out (`Arc` inputs, partitioned outputs) and the bring-up wrappers synchronize. Mixing cuTile's own streams with cudarc's cuBLASLt stream would need cross-runtime events at every hand-off.

cuda-oxide kernels, in contrast, compile ahead of time to plain PTX with a simple ABI: a raw pointer is one `u64` parameter, a slice is `(ptr, len)`, and scalars are scalars. cudarc can load that PTX and launch it on the same stream as cuBLASLt with no per-launch synchronization.

## Decision

1. **Streaming inference (batch 1, decode) runs on one CUDA stream:**
   - **GEMMs:** cuBLASLt via `s2s_cuda::gemm`, bf16 weights × bf16 activations → f32 (or strict f32 for parity runs).
   - **Everything else:** cuda-oxide SIMT kernels (`crates/s2s-simt`, module `infer`), launched through cudarc. This covers RMSNorm, interleaved RoPE, KV-cache append, split-K flash-decoding attention plus a combine pass, the SiLU-gated MLP, residual adds with layer scale, and f32→bf16 casts.
   - **Host synchronization** happens only when logits are read back (once per temporal step and once per depformer slice).
2. **The kernels' PTX is checked in** as `crates/s2s-gpu/src/s2s_simt.ptx`, generated by `scripts/build-simt-ptx.sh` (`--check` for CI). The stable-Rust workspace builds `s2s-gpu` without the cuda-oxide toolchain, and the driver JIT-compiles the PTX at load.
3. **The CPU keeps what needs exact host semantics or is cheap:** input embedding sums, depformer token embeddings, extra heads and **all sampling**. `LmModel` holds these and delegates the rest to an `LmAccelerator` (`s2s-model`), which `s2s-gpu::kyutai::GpuLm` implements. The multistream and ASR drivers and `KyutaiEngine` run unchanged on either backend.
4. **cuTile stays the choice for training kernels** (large, fixed-shape tiles where its JIT and tiling pay off), per ADR 0001. Revisit if cuTile gains stream-ordered launches on foreign streams and dynamic-extent loops.

## Verification (2026-11-09, L40S)

| Check | Result |
|---|---|
| GPU vs CPU port, reduced Moshi and STT fixtures, f32 weights, 17–20 frames with the rotating KV cache wrapping several times, plus a reset | worst relative error 2.4e-6, same greedy depformer tokens |
| Same, bf16 weights | worst relative error 2.5e-2 |
| Moshi 7B (`kyutai/moshiko-candle-bf16`), bf16 GPU vs f32 CPU | relative error 2.6e-2 on hidden state and logits |
| Moshi 7B frame time (temporal step + 8 depformer slices) | **24 ms** (real-time budget 80 ms; the CPU port takes ~18 s) |
| Unsupported configs (LayerNorm, sinusoidal positions, biases) | rejected at load with `Error::Unsupported` |

End to end, `s2s-kyutai-server` serves Moshi through `s2s-server`: GPU LM, CPU Mimi with pipelined decode, mean engine step 60 ms per 80 ms frame. Moshi's spoken replies, transcribed by our STT port, are coherent answers to spoken questions.

## Consequences

- **Two PTX build paths.** `cargo oxide` produces PTX for `s2s-simt`'s self-test and for `s2s-gpu`. The checked-in copy must be regenerated after kernel changes (`scripts/build-simt-ptx.sh`), and CI should run `--check`.
- **Raw-pointer kernels.** These kernels take raw pointers, so the launchers in `s2s-gpu/src/simt.rs` are the bounds checks. Each one asserts every buffer length before launching.
- **Unsupported configurations are rejected at load.** The supported subset is what Moshi v0.1 and DSM STT use: RMSNorm, SiLU gating, RoPE or no positions, no biases, head dim ≤ 256. LayerNorm, GELU MLPs and biases would need small extra kernels.
- **Next optimizations, not needed for real time on an L40S:**
  - CUDA graphs per temporal step and per depformer slice;
  - a bf16 KV cache (halves attention reads at full context);
  - Mimi on the GPU, which removes the CPU codec, the pipelining and its extra 80 ms of latency.
